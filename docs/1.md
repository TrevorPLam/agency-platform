I re-verified the critique claims before using them. Most were directionally helpful, but a few needed correction or tighter framing.

The most important corrections are these. Node 24 does **not** “end in October 2026” in the sense of becoming unsupported; October 2026 is when it leaves **Active LTS** and enters **Maintenance LTS**, and it remains supported until **April 2028**. Node 22 is already in **Maintenance LTS**, and Node 20 reaches end of life on **April 30, 2026**, so Node 20 should be treated as a compatibility floor for Next.js 16, not as a target for new production work. ([Node.js][1])

Corepack also needed nuance. It still ships with Node 24 and is still labeled **Experimental** in the Node docs, but Node says it will **no longer be distributed starting with Node.js v25**. That makes explicit package-manager pinning and documentation important now, even though the removal is not yet affecting Node 24 directly. ([Node.js][2])

The linting story also needed correction. In Next.js 16, `next lint` is gone, and the `eslint` option in `next.config` should be removed. But current Next docs still say that Next.js reports ESLint errors and warnings **during builds by default**. So a dedicated `lint` task in CI is still valuable for speed and clarity, but it is not accurate to say that `next build` stopped linting entirely. ([Next.js][3])

The `middleware.ts` to `proxy.ts` transition also needed nuance. Next.js 16 has renamed Middleware to Proxy, so migration-minded repos need to account for that rename. But a new app does **not** need a `proxy.ts` file unless it actually needs request interception, rewrites, redirects, header manipulation, or similar pre-route logic. Current docs also describe Proxy in ways that touch both Edge-oriented behavior and self-hosted Node.js scenarios, so Proxy should be treated as a **conditional file**, not a universal one. ([Next.js][4])

pnpm build approvals are in a transition state. The current stable `pnpm approve-builds` CLI still writes `onlyBuiltDependencies` and `ignoredBuiltDependencies`, while newer pnpm settings docs introduce `allowBuilds` as the preferred direction. So the guide below treats install-script approvals as an active security surface, but does not pretend the ecosystem has already converged on one final key name everywhere. ([pnpm][5])

Turborepo boundaries are real, but still experimental. They are worth planning for, but they should be treated as one layer of protection, not the only guardrail in the architecture. ([Turborepo][6])

I also **did not** carry over the critiques’ exact monthly hosting-cost estimates, because I did not verify those specific numbers from official pricing docs during this pass.

## Canonical guide for your firm’s repository

This guide is built around your actual situation: a digital marketing firm whose primary product is a marketing website, but whose codebase also needs to support client sites, internal or productized web apps like booking and analytics, and possibly a future mobile app. It is written as an **option-based system design**, not a one-path prescription. Every meaningful fork is presented as an option. The goal is to make the repository fully planned **without forcing decisions too early**. ([pnpm][7])

### Planning model

Every artifact in this guide belongs to one of four buckets:

`[C]` means common committed: files or directories that are broadly useful in this repository model.

`[O]` means option-specific committed: files that belong in Git **if** you activate that branch.

`[G]` means generated or local: files that should usually **not** be committed.

`[S]` means settings-only: controls that matter, but live in GitHub, Vercel, Expo, or another dashboard instead of Git.

That model is what makes the repository “fully accounted for” without pretending every branch is active at once. Next.js, pnpm, Turborepo, GitHub, Vercel, Cursor, Windsurf, and Expo all expose some combination of committed files, generated files, and settings-only controls, so a complete plan must cover all four buckets. ([Next.js][8])

## 1. Verified ecosystem baseline

### Runtime and package manager

You have three realistic runtime postures for a March 2026 build.

**Option A: Node 24.** This is the current **Active LTS** line and the most current LTS target for a fresh build. It remains supported through **April 2028**. This is the “latest supported LTS” branch. ([Node.js][1])

**Option B: Node 22.** This is already in **Maintenance LTS** and remains supported through **April 2027**. This is the “lower-change, shorter-horizon” branch. ([Node.js][1])

**Option C: Node 20 only as a compatibility floor.** Next.js 16 supports Node 20.9+, but Node 20 reaches end of life on **April 30, 2026**, so it is not a sensible target for new production work. ([GitHub][9])

For package management, `pnpm` remains a strong monorepo option because workspaces are built in, the workspace root is defined by `pnpm-workspace.yaml`, catalogs are supported there, and install-script approvals are now a first-class security topic. The root `packageManager` field should be treated as part of the architecture, not a nicety. ([pnpm][7])

A strict package-manager posture is a valid option. pnpm’s settings and package-manager behavior support tighter control, and the Node/Corepack changes make that more important over time. A looser posture is also viable, but it increases drift across machines and CI. ([pnpm][10])

### Monorepo orchestration

For orchestration, **Option A** is Turborepo. Its current model centers around a root `package.json`, a root lockfile, a root `turbo.json`, and `package.json` files inside each workspace package. Turborepo 2 uses the `tasks` key, not the older `pipeline` key, and it supports package-specific `turbo.json` files that extend the root config. ([Turborepo][11])

**Option B** is to use raw workspace scripts without Turborepo. That reduces file count and conceptual load, but gives up Turbo’s cache model, task graph, `--affected` workflows, remote caching, and generator tooling. ([Turborepo][12])

### Web framework

For the web stack, **Option A** is Next.js 16 App Router. The current official baseline includes stable Turbopack, React 19.2 support, new caching APIs, file-system conventions across `app/`, and current file-convention docs that are more extensive than older tutorials. `create-next-app` currently supports TypeScript, ESLint or Biome, and module path alias configuration. ([Next.js][13])

A `src/` folder is optional. Next supports both `src/app/...` and root-level `app/...`. Use whichever organization model you want, but be consistent repo-wide. ([Next.js][8])

### Deployment

For deployment, **Option A** is Vercel-managed monorepo deployment. One Git repository can back multiple Vercel projects, each with its own Root Directory. Vercel also supports skipping unaffected projects in monorepos, and the current docs explicitly say each workspace package must have a unique `name` and explicit internal dependencies in `package.json` so the dependency graph can be understood correctly. ([Vercel][14])

**Option B** is self-hosting Next.js. That remains viable, but the current self-hosting docs add meaningful runtime and infrastructure nuance, so this should be treated as a separate operational branch, not just “run `next start` somewhere.” ([Next.js][15])

**Option C** is mixed deployment, where sites and dashboards stay on a managed platform while a specialized API or worker service lives elsewhere. The monorepo structure below supports that because apps remain separate deployable units. ([Vercel][14])

### Governance and security

GitHub still gives you repository-level access control, path ownership through `CODEOWNERS`, rulesets with **Evaluate** mode, default CodeQL setup, dependency review, secret scanning, and push protection. Secret scanning for public repos is built in; private/internal org coverage depends on plan and product. GitHub also warns above **50 MiB**, blocks files over **100 MiB**, and recommends keeping repository size healthy, with a **10 GB** on-disk recommendation as a practical upper guideline. ([GitHub Docs][16])

### AI tooling

Cursor supports `.cursor/rules`, root and nested `AGENTS.md`, project-level CLI permissions via `.cursor/cli.json`, optional hooks via `.cursor/hooks.json`, `.cursorignore`, and Git worktrees for parallel agents. Windsurf supports directory-scoped `AGENTS.md`, `.windsurf/workflows`, `.windsurf/rules`, `.windsurf/hooks.json`, `.codeiumignore`, and workspace/global/system memories and rules. Next.js 16 also ships an MCP surface that makes `.mcp.json` an option for live app context during development. ([Cursor][17])

### Mobile

Expo currently has first-class monorepo support for Bun, npm, pnpm, and Yarn. EAS build files such as `eas.json` belong at the root of the app directory inside the monorepo. Since SDK 52, Expo’s Metro support for monorepos is much better, and if you use Expo’s current Metro config, you often do **not** need manual monorepo Metro setup anymore. `metro.config.js` remains a conditional file for custom bundler behavior, not a guaranteed baseline file. ([Expo Documentation][18])

## 3. Cross-cutting operating policies

### Security and patch posture

For a production firm repo, keep framework dependencies on current supported patches, not vague major ranges. Next has issued security updates for critical vulnerabilities in the RSC protocol, and its support policy expects users to stay current on supported lines. On GitHub, use Dependabot or an equivalent dependency-update workflow, enable CodeQL default setup, and add dependency review. Secret scanning and push protection should be enabled when available. ([Next.js][30])

### Environment variables and secrets

Do **not** commit real `.env*` files as a normal practice. Current Next docs say `.env` files are almost never meant to be committed, and `next-env.d.ts` should also stay out of Git. Commit `.env.example` files to document variable names, then choose one of three operational branches: platform-managed variables per deployed app, an external secrets manager, or local-only `.env.local` files for development plus platform secrets for hosted environments. ([Next.js][8])

Turborepo makes env handling architectural, not incidental. Its current docs explicitly warn that bad env handling can produce wrong builds and that `env` and `globalEnv` affect task hashing. So the repo should standardize env ownership per app and per task, not let every package improvise. ([Turborepo][31])

A good shared env package is one of the highest-leverage pieces in the repo. Plan for at least `client.ts`, `server.ts`, and `core.ts` or `shared.ts`, so browser-safe variables, server-only secrets, and framework-agnostic script variables are not mixed together. This is design guidance, but it is directly supported by the way Next, Turborepo, and multi-app deployments separate runtime contexts. ([Turborepo][31])

### CI/CD

If you use Vercel Git integration, you do **not** need a baseline GitHub deploy workflow for every Next app. Vercel already handles preview and production deployments by project. GitHub Actions should therefore focus on validation: install, lint, typecheck, test, build, security checks, dependency review, and any package-release automation. ([Vercel][14])

A healthy workflow family usually includes `ci.yml`, `security.yml`, `e2e.yml`, and optionally package-release or dependency-sync workflows. `actions/setup-node` supports caching package-manager metadata and `cache-dependency-path` when needed; it does **not** cache `node_modules`. pnpm CI examples also use `--frozen-lockfile` behavior by default. ([GitHub][32])

### Remote caching

If you adopt Turborepo, enable remote caching early. Turborepo’s CI docs use `TURBO_TOKEN` and `TURBO_TEAM` for remote cache access, and the cache can dramatically reduce repeated work across machines and CI. Turborepo also treats logs as artifacts, so do not print secrets or sensitive payloads in cacheable tasks. ([Turborepo][33])

### Pre-commit and dependency-sync policies

A pre-commit layer is an option, but a useful one. If you want one, `lefthook.yml` is a current, maintained hook configuration surface. For dependency alignment, Syncpack is a solid option on top of pnpm catalogs. For package versioning and changelogs, Changesets is the strongest branch when packages become semi-independent internal products. ([lefthook.dev][34])

### Package boundaries and imports

If you use Next.js App Router heavily, split truly interactive UI from server-safe UI. Next’s server/client component docs make it clear that client-only behavior belongs behind `"use client"`, while server-safe components should remain server-friendly by default. A practical package pattern is `packages/ui/src/server/*` and `packages/ui/src/client/*`, or at least a naming convention that makes the boundary obvious. `server-only` is also a useful safeguard for modules that must never leak into the client graph. ([Next.js][35])

### Local development

Turbo’s `dev` tasks are meant for long-running, persistent workflows, and the docs explicitly support filtered subsets of packages. So local development should be planned, not improvised: assign explicit ports per app, allow filtered `turbo dev` runs, and document local URLs for app-to-app communication. If one app needs to talk to another locally, use app config or a small local proxy strategy rather than hard-coded production endpoints. ([Turborepo][36])

### Self-hosting and Docker

If you keep a self-hosting option alive, plan it properly. Turborepo’s Docker guidance centers around `turbo prune --docker` to isolate the relevant app and its dependency graph for image builds. Do **not** assume that a monorepo app should install the whole workspace inside every production image. ([Turborepo][37])

### AI workflow policy

Treat AI context files as part of the repo contract. Root `AGENTS.md` should define architecture, boundaries, naming rules, and forbidden behaviors. Tool-specific files such as `.cursor/rules/*`, `.cursor/hooks.json`, `.windsurf/workflows/*`, `.windsurf/rules/*`, `.windsurf/hooks.json`, `.cursorignore`, and `.codeiumignore` are optional branches, but they are real control surfaces, not cosmetic extras. `.mcp.json` is the optional live-context branch for Next.js apps. ([Cursor][17])

## 13. Settings-only inventory

This is the part earlier drafts tended to under-specify. A repo tree is not complete unless the settings-only layer is named explicitly.

**GitHub settings**

* Rulesets, ideally using **Evaluate** before **Active**.
* Required reviews and, optionally, required code-owner reviews.
* CodeQL default setup.
* Secret scanning and push protection when available.
* Repository roles and outside-collaborator access.

**Vercel settings**

* One project per deployable app.
* Root Directory per project.
* Optionally include source files outside the Root Directory.
* Environment variables, domains, and Git branch/environment mapping.
* Related projects, rewrites, cron jobs, deployment protection, and project security settings.

**Expo/EAS settings**

* App-store credentials and EAS environment configuration.

These are all part of the architecture even though they are not committed files. ([GitHub Docs][16])

## 14. Decision dependencies and activation triggers

This is the part that turns the guide from a static tree into an operating model.

Add `apps/platform-api` when more than one frontend needs the same authenticated or data-mutating backend surface. Next’s own backend-for-frontend guidance now makes that a clean branch, but not a required day-one branch. ([Next.js][42])

Add `packages/db` when two or more apps share the same data domain, or when you need one place to manage migrations and seeds. Keep database tooling app-local if only one app truly needs it. ([Prisma][25])

Add `packages/tokens` when design tokens start coming from an external design process or when multiple frontends need generated token artifacts. Otherwise `packages/brand/src/theme.css` can be enough. ([Style Dictionary][47])

Add `.changeset/` when shared packages start behaving like products with intentional version upgrades. Add Syncpack when version skew across many manifests becomes annoying enough to deserve a machine-enforced policy. ([jamiemason.github.io][48])

Add `lefthook.yml` when you want fast local guardrails before CI. Keep it out until then if you prefer minimal local friction. ([lefthook.dev][34])

Add `.mcp.json` when AI agents need live app context, not just static code context. Add `.cursor/hooks.json` or `.windsurf/hooks.json` only when you really want automation on agent actions. ([Cursor][49])

Add `proxy.ts` only if the app actually needs that request boundary. If you are migrating an older app that has `middleware.ts`, plan the rename to `proxy.ts` as part of the migration branch. ([Next.js][4])

Add `instrumentation.ts`, `instrumentation-client.ts`, and Sentry/OpenTelemetry files when observability becomes an actual requirement, not as empty placeholder files. ([Next.js][50])

## 15. One low-decision starting profile, if you want it later

You asked not to turn decisions into defaults, so the guide above keeps everything optional. But one legitimate branch to keep in mind for later is a **low-decision starting profile**:

* one monorepo,
* Node 24,
* pnpm workspaces,
* Turborepo,
* Next.js 16 App Router,
* Vercel Git deployments,
* ESLint branch,
* local TypeScript/JSON content first,
* no DB/auth until needed,
* `packages/brand`, `packages/ui`, `packages/marketing`, `packages/env`, `packages/utils`, and `packages/types` first,
* AI context via root `AGENTS.md` plus `.cursor/rules`,
* GitHub rulesets, Dependabot, CodeQL, and secret scanning as soon as the repo exists.

That is only **one option**, not the guide’s imposed default. It exists to reduce decision fatigue if you later want a smaller first implementation surface. The official docs support all of those pieces well today. ([Node.js][1])

## 16. Completeness verdict

After re-verifying the critiques, re-checking the official docs, and closing the major gaps, the repository is now **fully accounted for at the planning level**.

That does **not** mean every branch has been chosen. It means every meaningful part of the system now sits in one of these buckets:

* common committed files,
* option-specific committed files,
* generated or local files,
* or settings-only controls.

The remaining unknowns are no longer hidden structural gaps. They are explicit branch choices: Node 22 vs 24, ESLint vs Biome, TypeScript/JSON content vs MDX vs CMS, Auth.js vs other auth branches, Prisma vs Drizzle vs no DB yet, Vercel-managed vs self-hosted, Expo vs no mobile, Stripe vs merchant-of-record, GA4 vs privacy-first analytics, and so on. That is the state you want before moving to creation order and starter contents. ([Next.js][8])

I researched the current official guidance for Next.js 16 App Router, Tailwind v4, shadcn/ui monorepos, Turborepo internal packages, and Next’s server/client component model. The strongest conclusion is this: for **spinning up simple client sites fast**, each client should be a **thin Next app** whose job is routing, metadata, assets, content, and theme overrides, while most rendering logic lives in a small set of shared packages. That conclusion is grounded in current docs: Next treats `page`/`layout` and metadata files as the routing surface, lets you safely colocate non-routable files, and supports route groups/private folders for organization; Tailwind v4 moves design tokens into CSS theme variables; shadcn recommends CSS-variable theming and now supports monorepos directly; Turborepo supports shared internal packages; and Next can transpile local workspace packages with `transpilePackages`. ([Next.js][1])

The practical implication is simple: **do not build each client app as a full standalone design system**. Build each client app as a **site shell + content + theme + assets + tiny custom overrides**. Put the real reusable work into packages. That gives you the fastest path to “new client site in hours” without locking every client into the exact same look and feel. ([Next.js][1])

## The focused architecture

For the version of the repo that gets you shipping client sites fastest, I would narrow the render-critical scope to this:

* `apps/client-<slug>-site/` for each client site.
* `packages/brand/` for design tokens, semantic theme variables, and theme presets.
* `packages/ui/` for primitives and layout utilities.
* `packages/marketing/` for reusable site sections, templates, and page rendering helpers.

Everything else can wait. Native apps, analytics packages, booking logic, deeper integrations, and complex data layers are later branches.

## What should live in a client folder

A client folder should own only the things that are **truly client-specific** or **must live at the app level because of Next.js conventions**.

That means a client app should own:

* route entrypoints like `layout.tsx` and `page.tsx`, because Next maps URLs through the file system and special files live in the app tree. ([Next.js][1])
* metadata files like `favicon.ico`, app icons, `manifest`, `robots`, and `sitemap`, because these are App Router file conventions tied to the app itself. ([Next.js][1])
* the app’s global CSS entry file, because Next recommends importing global styles and Tailwind stylesheets at the root and notes that CSS order depends on import order. ([Next.js][2])
* fonts applied at the root layout, because `next/font` is scoped to where it is used and should be attached to the root layout when you want app-wide typography. Next also recommends variable fonts for best performance and flexibility. ([Next.js][3])
* client-specific content and site configuration, because that is the actual tenant-specific data.
* client-specific assets in `public/`, because `public` is the static-asset folder. ([Next.js][1])
* only the one-off components that are unique to that client and not worth promoting into a shared package.

Everything else should be pushed down into packages.

## What should *not* live in a client folder

Do not put these in client apps unless they are truly one-off:

* shared buttons, cards, inputs, dialogs, accordions, nav menus, section wrappers
* shared hero sections, feature grids, FAQ blocks, testimonial bands, pricing sections, footers, CTAs
* shared class helpers like `cn`
* the semantic color/token contract
* reusable page renderers and SEO helpers
* any shared block schema/type system
* generic contact forms that work across clients
* theme presets that could be reused by more than one site

The reason is not only maintainability. In Next’s App Router, pages and layouts are Server Components by default, and `"use client"` creates a bundle boundary for the entire subtree below it. So if you keep reusable pieces shared and mostly server-safe, you reduce repeated client JavaScript and keep sites lighter. ([Next.js][4])

## The client app should be thin

The best mental model is:

* the **client app** chooses

  * brand preset
  * font choice
  * content
  * routes
  * assets
  * any bespoke one-off block

* the **packages** provide

  * how the site is rendered
  * how sections look and behave
  * the design token contract
  * the reusable components
  * the page-composition helpers

That is the balance that gives you both speed and flexibility.

### What each part does

`src/app/layout.tsx` is the site shell. It should import `globals.css`, load fonts with `next/font`, apply the chosen font class to `<html>`, and mount the shared header/footer or the shared page chrome. Next’s current font docs explicitly say fonts are scoped to where they’re used and should be placed in the root layout if they apply globally. ([Next.js][3])

`src/app/(marketing)/*/page.tsx` files should be mostly wiring files. Their job should be to import the page’s content/config and pass it into shared rendering helpers or blocks from `@firm/marketing`. They should not contain the full UI implementation for common sections.

`src/app/globals.css` should be the app’s CSS entrypoint. Next recommends importing global styles and Tailwind stylesheets at the root, and warns that CSS order is driven by import order. That makes `globals.css` the right place to import shared theme CSS first and client overrides last. ([Next.js][2])

`src/theme/client-theme.css` is where the client app should override semantic variables like `--primary`, `--background`, `--radius`, `--font-sans`, and any custom accents. This is where most per-client visual differentiation should happen.

`src/config/site.ts`, `navigation.ts`, and `social.ts` should hold non-page-specific config: brand name, site URL, locale, nav items, footer links, social URLs, contact details, and high-level SEO defaults.

`src/content/pages/*.ts` should hold the typed content for each page. For the fast-start branch, local TypeScript content is the most efficient option. MDX or a CMS can come later.

`src/app/(marketing)/_components/` should exist only for one-offs that belong to this client alone. Current Next docs explicitly support private folders prefixed with `_` for internal implementation details and say they are useful for separating UI logic from routing logic. ([Next.js][1])

## The `components.json` question

If you are using the shadcn CLI, then `components.json` matters. The current docs say `components.json` is optional in general, but it becomes important when using the CLI because it tells the tool how the project is set up and where to place generated resources. In monorepos, shadcn’s monorepo docs say each workspace involved in CLI installs should have a `components.json`, and the CLI can now install shared components into the shared `ui` package while placing app-specific compositions into the app. ([Shadcn UI][5])

That is extremely aligned with your goal:

* shared components stay in `packages/ui`
* client-specific assembled pieces stay in the client app

For your use case, that means the client app should keep a `components.json` **if** you want to use the shadcn CLI in that app. If you are not using the CLI there, you can skip it.

## The three packages to build now

If the goal is “spin up simple sites ASAP,” I would not start with ten packages. I would start with these three.

### 1. `packages/brand`

This is the design-token and theme-contract package. Its job is not to render pages. Its job is to define the **semantic styling contract** every client site can plug into.

Current Tailwind docs describe theme variables via `@theme`, and shadcn’s theming docs explicitly recommend CSS variables for theming and use semantic tokens like `background`, `foreground`, `primary`, and `primary-foreground`. That combination makes a semantic CSS-variable layer the best way to maximize flexibility with minimal per-client code. ([Tailwind CSS][6])

Recommended structure:

```text
packages/brand/
├─ package.json
├─ tsconfig.json
├─ src/
│  ├─ index.ts
│  ├─ theme/
│  │  ├─ contract.css
│  │  ├─ preset-neutral.css
│  │  ├─ preset-tech.css
│  │  ├─ preset-luxury.css
│  │  └─ preset-editorial.css
│  ├─ tokens.ts
│  └─ themes.ts
```

What belongs here:

* the semantic token contract: `--background`, `--foreground`, `--primary`, `--primary-foreground`, `--muted`, `--border`, `--ring`, `--radius`, etc.
* one or more preset theme files that establish a starting point for different types of brands
* optional token metadata and helpers

What should **not** go here:

* page layouts
* section implementations
* client-specific copy
* client-specific logos and photography

This package is the key to “maximum flexibility with minimal client work.” If shared components only depend on semantic variables, then a new client site mostly changes tokens, content, and assets rather than rewriting components.

### 2. `packages/ui`

This is the shared component system. It should contain low-level primitives and layout utilities, not client copy or client-specific business logic.

Next’s server/client component docs also make it important to keep interactive client code narrowly scoped, because once a file is marked `"use client"`, everything it imports joins the client bundle. ([Shadcn UI][7])

packages/ui/

Why this split matters:

* `server/` is for components that should stay server-safe by default
* `client/` is for components that truly need interactivity or browser APIs
* `components/` can hold neutral primitives that are safe to expose as public building blocks

If you use shadcn, `packages/ui` becomes the home for generated primitives. If you do not use shadcn, the same structural idea still holds.

## The best pattern for minimal client work and maximum flexibility

The best pattern is not “put absolutely everything in packages.” That would make client sites rigid. The best pattern is **shared rendering + app-level tokens + app-level content + app-level one-offs**.

The cleanest version of that is a four-layer model:

1. **Semantic theme contract** in `packages/brand`
2. **Primitive components** in `packages/ui`
3. **Reusable marketing sections and renderers** in `packages/marketing`
4. **Client-specific content, assets, and overrides** in `apps/client-<slug>-site`

That is what gives you speed without destroying creative flexibility.

### How styling should work

Use semantic CSS variables as the common contract. Tailwind v4’s `@theme` variables and shadcn’s recommended CSS-variable theming both point in the same direction: components should consume semantic tokens, not hardcoded brand colors. ([Tailwind CSS][6])

In practice:

* `packages/brand` defines the token names and some presets.
* `packages/ui` and `packages/marketing` style against semantic classes like `bg-background`, `text-foreground`, `bg-primary`, `text-primary-foreground`.
* each client app overrides those semantic variables in `src/theme/client-theme.css`.
* the client app’s `globals.css` imports shared theme CSS first and app overrides last.

That last import-order detail matters because Next’s CSS docs say CSS order depends on import order and recommend centralizing imports at the root for predictability. ([Next.js][2])

### How page rendering should work

For the fastest workflow, use a **hybrid page model**:

* simple shared pages are **block-driven**
* highly custom pages are **manually composed from shared blocks**
* only truly unique pieces stay local to the client app

That means a client home page can be mostly data:

* hero variant
* feature section variant
* testimonial set
* CTA style
* FAQ items

while a special campaign landing page can still be hand-built from shared blocks plus a small local custom component.

This hybrid model is the sweet spot. A fully hardcoded site makes every new client slow. A fully abstract site-builder can become rigid and painful. A hybrid gives you both speed and room to design.

## A stronger, thinner client app

If you want the client app as thin as possible, this is the mental rule:

* every `page.tsx` should mostly import content and call shared renderers
* every client app should have **one** CSS entrypoint
* every client app should have **zero** shared primitives duplicated locally
* every client app should have a small `_components/` folder only for one-off pieces
* every client app should own its theme override CSS, assets, metadata files, and content files

Because Next lets you safely colocate internal files in `app/`, and private folders explicitly opt folders out of routing, you can keep route-specific one-offs close to the route without polluting the shared packages. ([Next.js][1])

## Important app-level files that still matter even in a shared system

Even if packages do most of the work, these app-level files still matter:

`next.config.ts`
This is where the client app should list local workspace packages in `transpilePackages` when needed, so Next bundles them correctly from the monorepo. ([Next.js][8])

`package.json`
This is where the app declares workspace dependencies like `@firm/brand`, `@firm/ui`, and `@firm/marketing`. Turborepo’s internal-package docs show using workspace dependency syntax such as `workspace:*`. ([Turborepo][9])

`postcss.config.mjs`
Tailwind’s current Next.js install guide still creates this at the project root, which in a monorepo means each client app should have its own if it is a separate Next project. ([Tailwind CSS][10])

`components.json`
Needed only if you want shadcn CLI support in that workspace. Its `tailwind.css` path is configurable, which is useful in monorepos. For Tailwind v4, the shadcn docs say to leave the Tailwind config path blank. ([Shadcn UI][5])

## App-local CSS strategy: two valid options

There are two good ways to do CSS in this setup.

**Option 1: app-owned entry CSS, recommended for your use case.**
Each client app keeps `src/app/globals.css` as the root CSS entry. That file imports Tailwind, shared brand/theme CSS, and the client’s own override CSS. This gives maximum per-client control and matches Next’s recommendation to centralize CSS imports at the root. ([Next.js][2])

**Option 2: shared UI CSS entry.**
shadcn’s monorepo example shows a shared `packages/ui/src/styles/globals.css` and points the app’s `components.json` at it. This centralizes more, but it is less convenient when each client needs heavy custom theming. ([Shadcn UI][7])

For your agency use case, Option 1 is better because it preserves maximal client-side theme control while still sharing almost everything else.

## The one detail you should not over-centralize: fonts

Keep global font loading at the app level, inside the client app’s root layout. Next’s current docs explicitly say fonts are scoped to where they’re used and should be added to the root layout for app-wide use. They also recommend variable fonts for the best performance and flexibility. ([Next.js][3])

So:

* keep token names and typographic scale in `packages/brand`
* keep actual `next/font` calls in the client app’s `layout.tsx`

That is the cleanest split.

## Final answer to your core question

A client folder should contain:

* the Next app’s route files and root layout
* the site’s metadata files
* one global CSS entry file
* the client’s theme override CSS
* the client’s content and config
* the client’s assets
* only the truly bespoke components for that client

And to minimize work there while preserving maximum UI/UX flexibility, you should push into packages:

* the semantic theme system
* the shared primitives
* the reusable marketing sections
* the page renderer and SEO helpers

That is the highest-leverage version of your monorepo for starting sites fast. It uses the current grain of the Next.js, Tailwind, shadcn, and Turborepo ecosystems instead of fighting them. ([Next.js][1])

The next best step is to turn this narrowed architecture into a **creation-order guide** and **starter file contents** for one client app plus the three shared packages.

## 1. Decisions to make before creating files

You do not need to make every decision now, but you should decide the branches that affect the first files you create.

For runtime, the real choice is **Node 24** or **Node 22**. Node 24 is the newest Active LTS branch and is the best “fresh build” choice. Node 22 is acceptable if you want a slightly older LTS line, but it is already in Maintenance LTS. Node 20 is only a compatibility floor for Next.js 16, not a sensible target for new work in March 2026. ([Node.js][2])

For package management, the practical choice is **pnpm**. It gives you `pnpm-workspace.yaml`, catalogs, workspace-aware installs, and install-script approval controls. Keep the root `packageManager` field accurate, because it helps tooling and becomes more important as Corepack leaves the default Node distribution in v25+. ([pnpm][3])

For orchestration, the main choice is **Turborepo** or plain workspace scripts. If you want the simplest possible start, you can skip Turbo and just run pnpm workspace commands. If you want the repo to scale cleanly, Turbo is the better branch because it understands internal-package relationships, task graphs, package-level overrides, generators, and remote caching. ([Turborepo][4])

For app scaffolding, Next’s current CLI gives you three meaningful branches for linting: **ESLint**, **Biome**, or **None**. It also lets you choose TypeScript, Tailwind, `src/`, App Router, and import aliasing. For a site factory, the most common branches are TypeScript + Tailwind + App Router + `src/`, with either ESLint or Biome. ([Next.js][5])

For shared packages, the important decision is the **compilation strategy**. Turborepo currently documents three: Just-in-Time packages, Compiled packages, and Publishable packages. For your first site packages, Just-in-Time is the fastest to stand up because the consuming Next app can transpile local packages with `transpilePackages`. Later, if you want package build caching or stronger isolation, move those packages to the Compiled strategy. Publishable packages are the strictest and are a later branch. ([Turborepo][6])

For theming, the core decision is **semantic CSS variables** or **hardcoded per-client styles**. The docs strongly support the semantic-variable branch. Tailwind v4 treats theme variables as the design-token surface, and shadcn recommends CSS variables for theming. This is what gives you both speed and maximum UI/UX flexibility: shared components consume semantic tokens, and each client app overrides those tokens. ([Tailwind CSS][7])

For content, the fastest start is **local TypeScript content** in the client app. If you want MDX, add `mdx-components.tsx`. If you want a CMS, that becomes a later branch such as a Sanity studio app. The important point is that you should not force yourself into CMS complexity just to get simple sites out quickly. ([Next.js][1])

For deployment config, each Vercel app can use **`vercel.json`** or **`vercel.ts`**. `vercel.json` is the static branch; `vercel.ts` is the programmatic branch. Both live in the app root. ([Vercel][8])

## 2. Creation order

Phases 1 through 5 are enough to start spinning up real websites. Phases 6 through 9 are optional later branches.

### Phase 1 — create the root workspace

This phase creates the workspace shell that every client app and shared package will live inside. pnpm expects a workspace root and config in `pnpm-workspace.yaml`; Turborepo expects a root `turbo.json`; Next apps and internal packages need unique package names and explicit internal dependencies if you want clean monorepo behavior on Vercel. ([pnpm][3])

Create this first:

```text
/
├─ apps/
├─ packages/
├─ package.json
├─ pnpm-workspace.yaml
├─ pnpm-lock.yaml
├─ turbo.json
├─ .gitignore
├─ .nvmrc
├─ README.md
├─ .editorconfig                     [optional now]
├─ .gitattributes                    [optional now]
├─ .npmrc                            [optional]
├─ tsconfig.json                     [optional]
├─ eslint.config.mjs                 [optional, root-only]
├─ biome.json | biome.jsonc          [optional, choose one]
├─ AGENTS.md                         [optional]
├─ CLAUDE.md                         [optional]
├─ .cursor/                          [optional]
├─ .windsurf/                        [optional]
└─ .github/                          [optional now]
```

`package.json` is the root workspace entrypoint. It should be `private: true`, contain the `packageManager` field, and expose scripts that delegate to Turbo if you use Turbo, such as `dev`, `build`, `lint`, `check-types`, and `test`. Turborepo and Vercel both care about the root package manager and the root task graph. ([Turborepo][4])

`pnpm-workspace.yaml` is where the workspace is actually defined for pnpm. It should include your package globs, and it is also where catalogs live. If you choose install-script approvals, current pnpm stable writes `onlyBuiltDependencies` and `ignoredBuiltDependencies` here via `pnpm approve-builds`; newer docs preview `allowBuilds`, so treat this file as a living security surface. Authorization settings still belong in `.npmrc`, not here. ([pnpm][3])

`turbo.json` is the root task graph. It should define the shared tasks for the workspace and the cache behavior. Turbo’s current config surface is the `tasks` key, and package-level `turbo.json` files can later extend this root file with `extends: ["//"]`. ([Turborepo][9])

`.gitignore` should ignore real `.env*` files, `next-env.d.ts`, `.next/`, `.turbo/`, `.vercel/`, `node_modules/`, `dist/`, `build/`, coverage/test artifacts, and any generated folders from later branches like database clients or token builds. Next explicitly says `.env*` and `next-env.d.ts` should not be tracked. ([Next.js][1])

`.nvmrc` should be treated as common, not optional, because you do want toolchain consistency in a monorepo. If you later prefer Volta or another version manager, that is a branch change, but the repo should still pin the runtime somewhere. Node’s current LTS posture is the reason this file belongs at the root from day one. ([Node.js][2])

`README.md` should explain the repo at a high level: what lives in `apps/`, what lives in `packages/`, the chosen runtime, the chosen package manager, and how to start the first client site. Even if you later add docs, the root README remains the front door.

`tsconfig.json` at the root is optional. Turborepo’s current TypeScript guidance is that you only need a root TypeScript config if you actually keep TypeScript files at the root. If you want the cleaner branch, create a shared TypeScript-config package instead and let apps/packages extend from that. ([Turborepo][6])

### Phase 2 — create shared config packages

This is the phase that keeps linting and TypeScript from turning into app-by-app chaos. It is not strictly required to render the first site, but it is the cleanest early structure if you know this will become a multi-client repo. Turbo itself scaffolds repos with shared `eslint-config` and `typescript-config` packages in its examples and internal-package guidance. ([Turborepo][4])

Create these packages if you choose the structured branch:

```text
packages/
├─ typescript-config/
│  ├─ package.json
│  ├─ base.json
│  ├─ next-app.json
│  └─ package.json
└─ eslint-config/                   [ESLint branch only]
   ├─ package.json
   ├─ base.mjs
   ├─ next-app.mjs
   └─ node-package.mjs
```

If you choose ESLint, `packages/eslint-config` gives you one place to define common rules, and each Next app can have a tiny local `eslint.config.mjs` that imports the shared config and sets `settings.next.rootDir` when needed. Next’s docs explicitly show the monorepo `rootDir` pattern and the flat-config import style with `eslint-config-next/core-web-vitals`. ([Next.js][10])

If you choose Biome, do **not** create an `eslint-config` package. Keep one root `biome.json` or `biome.jsonc`, and add nested configs later only if needed. Biome’s nested-config branch is real, but it is not necessary to render sites on day one. Next’s CLI already supports Biome as a scaffold-time choice. ([Next.js][5])

### Phase 3 — create `packages/brand`

This package exists to make client apps thin. It should define the **semantic theme contract** that every shared component and every client site can rely on. Tailwind v4’s theme-variable model and shadcn’s CSS-variable theming both point to the same architecture: shared components should depend on semantic variables, not brand-specific hardcoded colors. ([Tailwind CSS][7])

Create this:

```text
packages/brand/
├─ package.json
├─ tsconfig.json
└─ src/
   ├─ index.ts
   ├─ theme/
   │  ├─ contract.css
   │  ├─ preset-neutral.css
   │  ├─ preset-tech.css
   │  ├─ preset-luxury.css
   │  └─ preset-editorial.css
   ├─ themes.ts
   └─ tokens.ts
```

`src/theme/contract.css` is the heart of the package. It should define semantic variables like `--background`, `--foreground`, `--primary`, `--primary-foreground`, `--secondary`, `--accent`, `--muted`, `--border`, `--input`, `--ring`, and `--radius`. If you are using Tailwind v4, this is also where you bridge those variables into your theme surface. If you are using shadcn, this contract should match the semantic variable names that its components expect. ([Tailwind CSS][7])

The preset files such as `preset-neutral.css` and `preset-tech.css` are the starting points for new client brands. They are not client-specific themes; they are reusable families that let a new site start with a coherent visual base before you add client-specific overrides.

`themes.ts` should export the names and metadata for the available presets. `tokens.ts` should export token metadata if you want to use tokens in TypeScript as well as CSS.

#### Optional branch: `packages/tokens`

If you know you want a design-token build pipeline now, add Style Dictionary as a separate package. Style Dictionary v4 uses an ESM/async model and can build multiple platforms from one token source. That makes it a valid optional branch, but not a requirement for the first sites. ([Style Dictionary][11])

```text
packages/tokens/
├─ package.json
├─ tsconfig.json                    [optional]
├─ config.json | config.js          [Style Dictionary default]
├─ sd.config.js | sd.config.mjs     [custom-location branch]
├─ build-tokens.js                  [Node API branch]
├─ src/
│  └─ tokens/
│     ├─ color.json
│     ├─ spacing.json
│     └─ typography.json
└─ build/                           [generated]
```

Use `packages/tokens` only if you want generated artifacts. If you just want fast client sites, `packages/brand` is enough.

### Phase 4 — create `packages/ui`

This package contains the reusable primitives and layout scaffolding. Its job is not to know anything about client copy or individual client branding. Its job is to render reusable building blocks that consume the semantic theme contract from `packages/brand`. Next’s Server/Client Component model also makes it worth separating server-safe UI from client-only UI so you do not accidentally bloat every marketing page with unnecessary client JavaScript. ([Next.js][12])

Create this:

```text
packages/ui/
├─ package.json
├─ tsconfig.json
├─ components.json                  [if using shadcn CLI]
└─ src/
   ├─ index.ts
   ├─ lib/
   │  └─ cn.ts
   ├─ server/
   │  ├─ container.tsx
   │  ├─ section.tsx
   │  ├─ heading.tsx
   │  ├─ prose.tsx
   │  └─ page-shell.tsx
   ├─ client/
   │  ├─ button.tsx
   │  ├─ input.tsx
   │  ├─ textarea.tsx
   │  ├─ dialog.tsx
   │  ├─ dropdown-menu.tsx
   │  └─ accordion.tsx
   └─ components/
      ├─ card.tsx
      ├─ badge.tsx
      ├─ separator.tsx
      └─ avatar.tsx
```

There are two viable branches here.

**Option A: shadcn-backed UI package.** Use `components.json` at the package root, let the shadcn CLI install shared UI primitives into this package, and keep the package aligned to shadcn’s current monorepo model. In Tailwind v4 projects, shadcn’s docs say the Tailwind config path should be left blank in `components.json`, and CSS-variable theming is the recommended theme strategy. ([Shadcn UI][13])

**Option B: hand-rolled UI package.** Skip `components.json`, but keep the same high-level split: layout primitives, interactive client primitives, and neutral display components.

`src/lib/cn.ts` is the shared class merge helper and belongs here if you use shadcn or similar class-composition patterns. `src/server/*` should stay server-safe by default. `src/client/*` is where files marked `"use client"` belong. This follows Next’s guidance that `"use client"` defines the client boundary for the component subtree. ([Next.js][14])

#### Package build decision for `ui`

For the fastest start, `packages/ui` can be a **Just-in-Time package**. Turborepo explicitly supports directly exporting TypeScript in JIT packages, and Next’s `transpilePackages` option lets the client app compile and bundle local packages from the monorepo. Later, if you want package-level build caching and `dist/` outputs, you can switch `ui` to a Compiled package. ([Turborepo][6])

The best early pattern is a **hybrid** one: block-driven pages for common cases, plus the ability to manually compose pages out of shared blocks when a client needs something bespoke.    │  │  └─ service-grid.tsx

   │  │  └─ logo-strip.tsx

The block files hold the real reusable website UI. The SEO helpers should centralize common metadata and JSON-LD generation so client apps only pass client-specific values. ### Phase 6 — create the client app template

This is the most important phase for your actual business. A client app should be **thin**. It should own routing, metadata, app-level CSS entry, fonts, content, config, assets, and any one-off bespoke components. It should **not** own the shared design system, reusable sections, or generic page-rendering logic. That division follows directly from Next’s App Router file conventions, Tailwind’s app-level CSS entry model, font scoping, and Turborepo/Next local-package consumption. ([Next.js][1])

   ├─ lib/
   │  └─ metadata.ts
   └─ fonts/                          [optional]

Here is the rule that should govern every client app.

Files that **must** stay in the client app are:

* App Router route files and special files such as `layout.tsx`, `page.tsx`, and metadata conventions, because Next maps those directly into routing and metadata behavior. ([Next.js][1])
* `globals.css`, because Next recommends importing global styles and Tailwind in the root layout and warns that CSS ordering depends on import order. ([Next.js][15])
* root font setup in `layout.tsx`, because fonts are scoped to where they’re used and should be attached to the Root Layout when they apply globally. ([Next.js][16])
* client-specific content, config, and assets.
* truly one-off bespoke components.

Files that should **leave** the client app and move into packages are:

* reusable primitives
* reusable site sections
* reusable SEO helpers
* shared layout wrappers
* shared semantic theme contract
* any component or section used by two or more clients

That rule is the main way you keep client apps thin while preserving maximum flexibility.

#### What each client-app folder is for

`src/app/layout.tsx` is the site shell. It should import `globals.css`, set the global font, and mount your shared marketing shell. `src/app/globals.css` should import Tailwind and any shared theme CSS, then import the client’s own theme overrides after the shared imports. Next’s CSS docs explicitly recommend containing CSS imports to a small number of entry files and importing global/Tailwind styles at the root. ([Next.js][15])

`src/theme/client-theme.css` is the client’s real styling surface. This is where the client overrides semantic variables such as brand colors, radii, shadows, and any extra accents. That is how you maximize flexibility without rewriting shared components.

`src/config/site.ts`, `navigation.ts`, and `social.ts` are site-wide config, not page content.

`src/content/pages/*.ts` is the fast-start content branch. It keeps content local, typed, and easy to edit without introducing MDX or CMS complexity.

`src/app/(marketing)/_components/` is where one-off client-only components belong. Next’s private-folder convention explicitly supports `_folder` for non-routable implementation details, and route groups like `(marketing)` let you organize sections without changing the URL. ([Next.js][1])

#### Content-source branches for the client app

**Option A: local TypeScript content** is the fastest branch and should be your default for the first several sites.

**Option B: local MDX** adds `mdx-components.tsx` and local content folders.

**Option C: CMS later** moves content editing out of the app, but the client app still consumes shared packages and keeps the same route shape. ([Next.js][17])

#### Styling branches for the client app

**Option A: app-owned CSS entrypoint** is the best branch for an agency. Each client app owns `globals.css` and `client-theme.css`, while importing shared brand CSS and shared component CSS expectations. This gives every client the strongest override surface while keeping the shared packages reusable. Next’s CSS docs support this structure cleanly. ([Next.js][15])

**Option B: package-owned CSS entrypoint** centralizes more styling inside shared packages. This is a valid branch, especially if you want a stricter design system, but it reduces per-client override flexibility.

#### shadcn in the client app

If you want to run the shadcn CLI inside the client app, keep `components.json` there. If the app only consumes shared components from `packages/ui`, you can skip it. shadcn’s docs are explicit that `components.json` is optional unless you are using the CLI. ([Shadcn UI][18])

### Phase 7 — create the first real client site

Once the template exists, a first real client site should mostly be data and overrides, not architecture work. This is where the thin-app model pays off.

The shortest route is:

1. create `apps/client-acme-site`
2. choose a theme preset from `packages/brand`
3. set the font in `layout.tsx`
4. fill `src/config/*`
5. fill `src/content/pages/*`
6. add client images and logos to `public/`
7. create any tiny one-off pieces in `src/app/(marketing)/_components/`
8. wire page route files to shared renderers and blocks

That flow follows the architecture above and keeps the client folder limited to what is truly client-specific.

A marketing site should generally start with these route files:

* home
* services
* contact
* privacy
* terms

Then add about, work/case studies, and blog only when the client actually needs them.

For every new client, `package.json` should depend on the shared packages explicitly, for example `@firm/brand`, `@firm/ui`, and `@firm/marketing`. If you are using Vercel monorepo deployments and want skip-unaffected-projects behavior to work correctly, those internal dependencies must be declared explicitly and each workspace package must have a unique `name`. ([Vercel][19])

Also, keep client assets web-ready. GitHub warns above 50 MiB, blocks files above 100 MiB, and recommends keeping repositories small. Raw design exports, videos, PSDs, Figma exports, database dumps, and analytics exports do not belong in normal Git history. If you must track large binaries, use Git LFS and commit `.gitattributes`. ([GitHub Docs][20])

### Phase 8 — optional day-one quality files

These files do not render the site, but they are the next most useful layer once the first client site works.

If you want GitHub repo standards immediately, create:

```text
.github/
├─ CODEOWNERS
├─ dependabot.yml
├─ pull_request_template.md
├─ ISSUE_TEMPLATE/
│  ├─ bug-report.yml
│  ├─ feature-request.yml
│  └─ config.yml
└─ workflows/
   ├─ ci.yml
   ├─ e2e.yml
   └─ security.yml
```

GitHub supports issue templates and issue forms in `.github/ISSUE_TEMPLATE`, PR templates in root, `docs`, or `.github`, and CODEOWNERS for path-based ownership. Rulesets are settings-only rather than files, but they are the preferred governance layer over time. ([GitHub Docs][21])

If you want AI-tooling control files early, create:

```text
AGENTS.md
CLAUDE.md
.cursor/
  rules/
.windsurf/
  workflows/
.mcp.json
```

Next’s AI-agents guide explicitly supports a root `AGENTS.md`, and its MCP guide documents the current MCP server path for live application context. Cursor and Windsurf both support repo-level AI guidance files and scoped instructions. ([Next.js][17])

If you want pre-commit hooks early, add `lefthook.yml`. If you want package version governance later, add a Changesets branch. If you want dependency range enforcement later, add a Syncpack branch. These are useful, but not rendering-critical, so they should not block the first sites.

## 3. The rule that keeps client folders minimal and flexible

Use this promotion rule across the whole repo:

If a file is a route, metadata convention, asset, site config, page content module, theme override, font setup, or a one-off bespoke section for one client, it stays in the client app.

If a file is a reusable primitive, reusable marketing section, reusable layout piece, semantic token contract, or a helper used by two or more clients, it belongs in a package.

That rule is the real engine of the architecture. It is what lets client folders stay tiny without killing design freedom.

## 4. The shortest viable path

If your only goal is to start spinning up simple sites immediately, the shortest viable path is:

1. Phase 1 root workspace
2. Phase 2 shared config packages
3. Phase 3 `packages/brand`
4. Phase 4 `packages/ui`
5. Phase 5 `packages/marketing`
6. Phase 6 `apps/client-<slug>-site` template
7. create `client-acme-site` from that template

That is enough to render and ship real websites. Everything else in this guide is a later branch, not a blocker.
