# Versioning and releases

Design-system-related packages in this monorepo (e.g. `@agency/ui`, `@agency/design-tokens`) are versioned with **semantic versioning** and **Changesets**. This document describes how versions work, what counts as breaking, and how to cut releases. For broader design-system delivery guidance, see [docs/RESEARCH_MARKETING_MONOREPO_DESIGN_2026.md](./RESEARCH_MARKETING_MONOREPO_DESIGN_2026.md) §3a.

---

## Semantic versioning (semver)

We use **MAJOR.MINOR.PATCH**:

| Bump   | When to use |
|--------|-------------|
| **PATCH** | Bug fixes, non-breaking token value tweaks, docs-only. |
| **MINOR** | New components, new optional props, backwards-compatible features. |
| **MAJOR** | Breaking changes (see below). |

---

## What counts as breaking

**Design:** Token renames or removals; token value changes that change layout or appearance in a way consumers rely on; removal or behavioural change of overridable elements; typography or component width changes that cause layout shift; component removal.

**Implementation:** Renaming or removing components or props; removing exports; dependency version changes that drop support (e.g. Node or React); box-model or alignment changes that break existing layouts.

**Non-breaking:** Deprecation warnings (until the actual removal), bug fixes, new optional props, internal refactors that preserve public API and behaviour.

---

## Support window

We support **current major + previous major**. After a MAJOR release, the previous major may receive security/patch fixes for a defined period (e.g. 6 months); document the exact window in release notes or GOVERNANCE when adopted.

---

## Changesets workflow

1. **When making a change** that affects a publishable package (e.g. `@agency/ui`, `@agency/design-tokens`), add a changeset from the repo root:
   ```bash
   pnpm changeset
   ```
   Choose the packages and bump type (major / minor / patch), and add a short description. Commit the new file under `.changeset/`.

2. **Version (apply changesets):** When preparing a release, run:
   ```bash
   pnpm version
   ```
   This updates `package.json` versions and CHANGELOGs from the current changesets, then removes the consumed changeset files.

3. **Publish:** If you publish to npm (or another registry), run your publish command (e.g. `pnpm publish -r` from root, or per-package) after `pnpm version`. The repo is currently configured with `"access": "restricted"` in `.changeset/config.json`; change to `"public"` for public npm packages.

Changelogs are generated by Changesets and committed when you run `pnpm version`.

---

## Release cadence (guidance)

- **Patch:** As needed (bug fixes, non-breaking token tweaks).
- **Minor:** When adding new components or backwards-compatible features (e.g. biweekly or per milestone).
- **Major:** With a review window (e.g. 10 days) and a clear migration path; document deprecations and, where feasible, provide codemods for renames and prop migrations.

These are guidelines; adjust to team size and release process. For formal roles and cadence, see [docs/GOVERNANCE.md](./GOVERNANCE.md) when adopted.
